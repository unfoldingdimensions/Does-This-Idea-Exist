Recommended direction
Reframe the product from:

“Does this startup exist?”

to:

Find products that already exist, understand the closest alternatives, and decide what would be meaningfully different before you build.

Keep “Does this startup exist?” as the hook and brand personality, but make the core output a research result—not a binary verification badge.

Killer workflow
A new user should be able to do this in under two minutes:

Enter a product name, URL, GitHub repository, or plain-English idea.
Receive results grouped into:
Direct matches — essentially the same product.
Closest alternatives — solving the same problem differently.
Related products — adjacent tools worth studying.
See why each result matched.
Open a product dossier containing:
What it does.
Target user/problem.
Website, demo, docs, and GitHub links.
Activity and freshness signals.
Human review date.
Evidence sources.
Caveats and unknowns.
Select up to three products for comparison.
Answer: “What would be different about your version?”
Share or export the research.
The success event is:

The user finds a relevant existing product and understands how it relates to their idea.

Not merely opening a card.

Phase 2: Fix data integrity and search
Duplicate and identity cleanup
The current URL normalization is a good foundation in backend/app/db.py:81-108, but it is not enough.

Add:

Canonical domain.
Normalized GitHub owner/repository.
Redirect destination tracking.
Alias URLs.
Duplicate candidates based on name + domain + description similarity.
Admin duplicate-review queue.
Conservative merge behavior that preserves:
Strongest verification state.
Historical review records.
Alternate URLs.
Source provenance.
Do not automatically merge ambiguous companies that merely share a name.

Search
The current relevance ordering in frontend/lib/search.ts:62-82 is better than the earlier implementation, but the next version should classify matches:

Exact product name.
Exact domain.
Phrase/name match.
Tagline match.
Problem-description match.
Category/keyword match.
Fuzzy fallback.
Stars should only be a tiebreaker.

Each result should eventually show a short explanation such as:

“Exact name match”
“Matches your idea’s product category”
“Similar problem description”
“Same audience, different approach”
Add regression tests for:

Exact product names.
Domains.
Multi-word ideas.
Synonyms.
Unrelated fuzzy matches.
Empty results.
Duplicate records.
Phase 3: Replace the overloaded trust model
The current Verified state means roughly “a human checked this and it appeared alive.” That must be made explicit.

Use separate evidence dimensions:

Website reachable
Product evidence found
Repository active
Company identity confirmed
Human reviewed
Last checked
Status history
Public copy should say:

Human reviewed — evidence checked on [date]. This is not an endorsement.

Do not let “Verified” imply:

The company is legitimate.
The product is good.
The company has customers.
The business is active.
The product is safe.
The startup is investable.
Add a prominent “How this archive works” explanation:

Unverified means “filed, awaiting review.”
Reachable means “the URL responded.”
Dead means “repeated checks found the product unavailable.”
Human reviewed means “a curator inspected the available evidence.”
Unknown should remain a valid answer.
This directly addresses the “shelf of unread files” criticism from dogfood-output/adversarial-ux-report.md:23-28.

Phase 7: Enrich data carefully
Do not begin with uncontrolled web scraping. It will create:

Stale data.
Duplicate entities.
Legal and terms-of-service risk.
Attribution problems.
Maintenance burden.
Low-quality volume.
Use this source order:

Existing archive.
GitHub API and repository activity.
Existing website metadata and redirect checks.
Wayback metadata.
Curated URL lists.
Permitted public APIs or datasets.
Only then, carefully selected scraping.
Every imported fact should record:

Source URL.
Capture date.
Import method.
Whether it was human-reviewed.
Whether it is a fact, inference, or generated summary.
Build one adapter at a time. Each adapter should support deduplication, rate limits, retries, resumable jobs, and an import report.

The local-first model can remain the default while offering a hosted read-only archive later.

Validation plan
Test with 10–20 founders, indie hackers, product strategists, or investors using real ideas.

Ask them to research three ideas and measure:

Did they find a relevant product?
Was the first result useful?
Did they understand why it matched?
Did they open evidence links?
Did they compare products?
Did they export or share the result?
Did they return for another idea?
Did they understand “verified” correctly?
Would they use it again instead of Google?
Would they contribute a missing product?
Initial targets:

Exact matches appear first.
No duplicate identity with conflicting status.
At least 80% of test queries have a relevant result in the first three results.
Every trust claim has visible evidence or says “unknown.”
New users understand the trust model without explanation from us.
Users complete a search-to-dossier flow in under two minutes.
At least a few users research multiple ideas during the same session.
The strongest signal is repeated research—not compliments about the interface.

Recommended implementation sequence
Baseline data and product-contract document.
Duplicate and identity audit.
Search relevance regression suite.
Trust copy and evidence explanation.
Research result sections.
Evidence/provenance schema.
Product dossier and stable URLs.
Comparison and export.
GitHub and Wayback activity enrichment.
One permitted external source adapter.
Founder usability testing.
Iterate based on actual failed searches.
The first coding slice should not be scraping or semantic AI search. It should be:

Audit the current data, remove identity conflicts, improve search explanations, and make the trust model precise.

That gives the new product direction a reliable foundation before adding more data or complexity.
